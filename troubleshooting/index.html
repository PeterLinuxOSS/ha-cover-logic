    Troubleshooting¶

    Why did this blind move, or not move?¶

    Start with sensor.cover_logic_mode's trace attribute — it names the exact rule (mode.zone#index) that decided every blind's current target, including #none for "nothing matched". If the label is not the one you expected to fire, the question becomes "why didn't my rule match", which is usually a condition that is not reading what you think it is reading, or an earlier rule in the same list matching first. If the label is mode.*#index rather than mode.zone#index, the zone fell through to the mode's shared default list — see rules: inherited defaults.

    If trace looks right but the blind still did not physically move, work through the cases below in order — they are the three places a decided action can still fail to become a command.

    The blind never appears in the log at all¶

    If nine blinds get a log line on a recompute and one does not, that missing one is the tell — not an error message, just silence. Check sensor.cover_logic_mode's readiness.blocked attribute for that blind's entity id. If it is there, the list beside it names which entities this blind's own decision depends on that are currently unreadable (absent, unknown, or unavailable, and read by a node with no stated default:). This is a veto, not a timeout — the engine still decided something, and targets/trace still show it, but the executor refuses to act on a decision made from a world it could not fully read. Fix the underlying entity (restore it, wait for it to populate after startup) and the veto lifts on the next evaluation with no further action needed.

    A readiness.missing entity with no blind named in readiness.blocked is still worth checking — it means something in the configuration reads an unready entity that happens not to gate any blind yet, which is still usually worth fixing before it does.

    The blind is waiting and did not move¶

    Check pending.deferred for the blind's entity id. If it is there, a defer-policy guard is holding it: the attribute names which guard, how long it has waited, and what happens when max_wait runs out (proceed or abandon). This is expected, working behaviour for a guard like the one in door interlock — the blind is not stuck, it is correctly waiting for the condition that is deferring it (an open door, a running sauna, whatever the guard watches) to clear.

    Also check pending.queued — a blind already mid-sequence (a position move still running, with a tilt move queued behind it) will not react to a new decision until that sequence finishes or is superseded; step shows how far through it is.

    The blind moved once by hand, and now ignores the configuration¶

    Check manual_holds for the blind's entity id. If it is there, someone (or something with a user_id on its context) moved this blind directly, and manual_detection.hold is deliberately withholding the rule-decided target until the mode or that target changes — usually at the next mode switch, which releases the hold even if the new mode decides the same target. This is the feature working as intended, not a bug: re-sending the old target on every recompute is exactly what hold exists to prevent. Holds are kept in memory only, so a Home Assistant restart or an integration reload also clears them.

    If a blind moved by voice is not being held at all even though hold is on, see manual moves: the voice limitation — this is a known Home Assistant limitation this integration cannot see around, not a misconfiguration.

    I changed the configuration and nothing happened¶

    Editing through the UI or importing a YAML file schedules an automatic reload a couple of seconds after the last write settles — you should not need to reload the integration by hand for an ordinary configuration edit. If a change genuinely does not seem to be taking effect:

    1. Give it a few seconds. A burst of writes (an import touching many subentries, several quick edits in a row) coalesces into one reload after the writes stop, not one reload per write.
    2. Confirm via trace, not by re-reading the configuration. The subentries on screen can be exactly what you intended and the running decision can still be built from an older Config object if the reload has not happened yet — trace is generated by whatever configuration is actually loaded right now, so a label that still reflects the old rule names or the old zone structure is the proof a reload has not landed, independent of what the options screens show you.
    3. Check Settings → Devices & services → Cover Logic for a Reload option if you suspect a reload never got scheduled at all — this forces the same reload by hand.
    4. One option is read only at the moment the integration starts up, not live: the Fixture to compare against path (Configure → Execution). Changing it still schedules the same automatic reload as any other configuration write, so the sequence above applies to it too — but if you are specifically troubleshooting fixture drift and just changed that path, give the reload the same few seconds before concluding the comparison is wrong.

    dry_run and dead_band, by contrast, are read live from the entry's options on every evaluation and never need a reload at all — if one of those two seems not to have taken effect, the more likely explanation is that the change was not actually saved, not that it needs more time.
